# Robust-Rail Planning 
An AI Planning approach to solving the TUSPwSS.


- [Documentation on the Problem class in unified-planning (Python)](https://unified-planning.readthedocs.io/en/latest/api/model/Problem.html)
- [Documentation on the PDDL.jl representation of PDDL (Julia)](https://juliaplanners.github.io/PDDL.jl/stable/tutorials/getting_started/)
- [Documentation on the SymbolicPlanners.jl library (Julia)](https://juliaplanners.github.io/SymbolicPlanners.jl/dev/)

## Structure
- `src`
  - `robust_rail_planning/`
    - `converter.py`: converts PDDL `.plan` files to TORS JSON format
    - `cli.py`: where the CLI arguments are defined
    - `evaluate.py`: calls the TORS evaluator via Docker
    - `pipeline.py`: runs the pipeline end to end for a number of instances
    - `plan/`: contains any code for updating/running a planner (using SymbolicPlanners.jl)
  - `convert/`: legacy converter variants (see *Converter variants* below)
- `run.py`: interactive runner for converting and planning (choose location, scenario, action) does not use tors evaluation
- `test_data/`: pre-made plans and scenarios for quick testing
  - `plans/`: `.plan` files and `.json` TORS plan files
  - `plans_converted/`: converter output (generated by `--test-eval`)
  - `scenarios/`: solver and TORS scenario JSON files
- `data` contains any PDDL files, make sure to keep versions separate 

## Usage
Run commands from the `planning-approach` folder in the main repo, not from inside the dev container.

```
cd planning-approach
```
1. Build the project using a setup script:

Linux/macOS:
```
bash setup.sh
```
Windows PowerShell:
```
.\setup.ps1
```
Windows Command Prompt:``
```
setup.bat
```

2. Activate the Conda environment
```
conda activate robust-rail-planning
```

3. Run the pipeline using one of the commands below.

### CLI flags

| Flag | Description |
| --- | --- |
| `--generate` | (Re)generate scenarios before planning |
| `--examples` | Run only `scenario_solver_example*.json` files |
| `--simple` | Run the pipeline on the simple scenario and evaluate with TORS |
| `--test-eval` | Run pre-made plans through the converter and/or TORS evaluation (see below) |
| `--planner {astar,enhsp}` | Planner backend to use (default: `enhsp`) |
| `--model MODEL` | PDDL model/converter to use. |
| `--ignore-time` | Ignore timing constraints during TORS evaluation (allows trains to exit after their incoming match arrives rather than at the exact scheduled time) |
| `--solve` | Run the C# local-search solver on each scenario instead of the PDDL planner |
| `--use-tors` | Run TORS evaluation after planning. Only needed for `--examples` and `--generate` modes; `--simple` and `--test-eval` always evaluate with TORS |
| `--log-level LEVEL` | Set logging verbosity (default: `INFO`) |

```robust-rail-plan```

```robust-rail-plan --generate```

```robust-rail-plan --examples```

```robust-rail-plan --simple```

```robust-rail-plan --examples --model corridor_no_switch_unlimited_order_servicing_discrete_compiled_matching --planner enhsp```

```robust-rail-plan --test-eval --ignore-time```

```robust-rail-plan --log-level DEBUG```

### `--test-eval`

Evaluates pre-made plans against the TORS shunting simulator.
Place plan files in `test_data/plans/` and matching scenario files in
`test_data/scenarios/`. The naming convention links them:

```
scenario_solver_example1.plan   -> solver scenario: scenario_solver_example1*.json
                               -> TORS scenario:    scenario_example1*.json

scenario_solver_example1.json   -> TORS scenario:    scenario_example1*.json
```

The command handles two cases:
- **`.json` TORS plans** (contain an `"actions"` key) are sent to TORS directly.
- **`.plan` files** (PDDL output) are first run through the converter, then
  evaluated by TORS.

Converted plans are saved to `test_data/plans_converted/` and evaluation
results are written to `data/tors_eval_results/`.

Docker must be running for TORS evaluation.

### `run.py` (interactive)

`run.py` provides a menu-driven interface for the full pipeline.
It discovers locations and scenarios from `scenario-planning-inputs/`, then
lets you pick a conversion, planning, or validation step:

```
python run.py
```

Actions available:
1. **Convert to PDDL** — convert a solver scenario to PDDL problem/domain files
2. **Run planner** — run SymbolicPlanners.jl or ENHSP on a converted problem
3. **Convert then plan** — both steps in sequence
4. **Validate plan** — check a plan against the PDDL domain and problem (not tors)
5. **Convert then plan then validate**

### Plan visualizer

A web-based visualizer renders scenario and plan data as an interactive
HTML page. Start it from the repo root:

```
python planning-approach/tools/plan_visualizer/run_existing_visualizer.py
```

By default the server listens on `http://127.0.0.1:8767`. Open that URL in
a browser, then use the dropdowns to select a location, scenario, and plan
and click **Generate & View**. The generated HTML is saved to
`planning-approach/data/` and loaded in an iframe on the page.

Use `--port` to change the listen port:

```
python planning-approach/tools/plan_visualizer/run_existing_visualizer.py --port 9000
```

## Converter variants

| Converter | Main difference |
| --- | --- |
| `corridor_no_switch_unlimited_order_servicing_discrete_compiled_matching` | Uses composition-preserving pre-matching and lower-arity request actions. Complete incoming compositions are reused where possible; other compositions can be uncoupled, moved, and assembled from the front or back. It produces a scenario-specific domain for the selected request sequence. |

Earlier converter variants are retained under `src/convert/archive/` for
reproducing older modelling experiments, but are not exposed by the planning
pipeline.

### Compiled-matching results

ENHSP runs using the compiled-matching converter produced the following search
results:

| Scenario | Planning time | Plan length | Expanded nodes |
| --- | ---: | ---: | ---: |
| `scenario_solver_example1.json` | 3.429 s | 41 | 617 |
| `scenario_solver_example2.json` | 0.236 s | 24 | 29 |
| `scenario_solver_example3.json` | 0.239 s | 21 | 24 |
| `scenario_solver_random1.json` | 1.934 s | 93 | 169 |

The plans can also be checked with the AI-generated `validate_plan.py` and
`audit_discrete_plan.py` scripts. These validation scripts have not yet been
thoroughly independently verified. The two random-distribution scenarios are
not included in these results.
